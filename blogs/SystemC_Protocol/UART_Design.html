1. Introduction

The Universal Asynchronous Receiver/Transmitter (UART) is a simple yet powerful serial communication protocol that has been around for decades. It enables point-to-point data transfer using just two main lines, transmit (TX) and receive (RX). It is asynchronous, meaning that it doesn’t have a shared clock signal. It still continues to be widely used in microcontrollers, FPGAs, industrial equipment, despite the emergence of faster and more complex protocols like SPI or I2C, because of its simplicity, low hardware requirements, and proven reliability.

Photo from here

The image above shows a UART communication setup between two devices. In a real-world scenario, Device 1 could be a PC, microcontroller or another FPGA sending data to Device 2, which processes the data and sends a response back.

In this project, we are only designing UART logic for Device 2. Device 1 will not be implemented on hardware; instead, its behavior will be generated from a testbench in simulation. The testbench will send bytes of data to Device 2. Device 2 will accept the data and send back the processed data to the testbench.

In this post, we will see how the UART logic can be designed using a simple finite-state machine (FSM). The data transmission follows a well-defined sequence: waiting in the idle state, detecting a start bit, shifting in or out data bits, verifying the stop bit, and returning to idle.

2. Background: UART Essentials

UART communication is asynchronous, meaning the device 1 transmitter and the device 2 receiver do not share a common clock signal. Each operates on its own clock, and both ends agree beforehand on a baud rate.

Photo from here

Baud rate generation and clock-to-bit timing

The baud rate is the number of bits transmitted per second. Since UART does not send a clock signal, each side must generate its own timing internally.

Bit Period (seconds) = 1 / baud rate

Clock cycles per bit = System clock frequency / baud rate

Common pitfalls

Sampling errors and metastability can degrade communication quality. Designers typically use oversampling and synchronizer flip-flops to minimize these risks.

3. Designing the RX FSM

The RX FSM reconstructs a byte from the serialized RX line. It detects a start bit, samples each data bit at the midpoint of the bit period, checks the stop bit, and raises a data-valid pulse once a complete frame is received.

4. Designing the TX FSM

The TX FSM serializes data for transmission. It sends a start bit, data bits LSB-first, and a stop bit, holding each bit for a precise number of clock cycles derived from the baud rate.

5. Top-Level Integration

At the top level, the design integrates the RX and TX blocks around a shared clock-cycles-per-bit parameter.

6. Verification: Testbench & Simulation

A self-checking testbench generates UART frames, captures transmitted data, and compares it against expected values. Synchronization and mid-bit sampling ensure robust reception.

7. On-Board Testing & Validation

A) External USB-UART dongle

A USB-UART adapter connects the FPGA UART to a PC terminal for real-world testing.

B) On-chip CPU driven self-test

On Zynq platforms, the CPU can communicate with the UART RTL via EMIO, enabling full on-board validation without external hardware.
