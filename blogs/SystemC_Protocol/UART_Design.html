1. Introduction

The Universal Asynchronous Receiver/Transmitter (UART) is a simple yet powerful serial communication protocol that has been around for decades. It enables point-to-point data transfer using just two main lines, transmit (TX) and receive (RX). It is asynchronous, meaning that it does not rely on a shared clock signal. Despite the emergence of faster and more complex protocols such as SPI and I2C, UART continues to be widely used in microcontrollers, FPGAs, and industrial systems due to its simplicity, low hardware overhead, and proven reliability.

Image source: vanhunteradams.com

The diagram above illustrates a typical UART communication setup between two devices. In practice, Device 1 may be a PC, microcontroller, or FPGA transmitting data to Device 2, which processes the data and optionally sends a response. In this project, we design UART logic only for Device 2. Device 1 is emulated in simulation using a testbench that generates UART frames.

The UART logic is implemented using finite-state machines (FSMs). Both transmission and reception follow a structured sequence: idle detection, start-bit handling, data shifting, stop-bit verification, and return to idle. FSM-based design ensures deterministic timing, clean phase transitions, and structured error handling such as framing violations.

This post first reviews UART signaling and timing fundamentals, then presents RX and TX FSM designs, followed by top-level integration, simulation-based verification, and on-board validation considerations.

2. Background: UART Essentials

UART communication is asynchronous, meaning the transmitter and receiver operate on independent clocks. Both ends must agree on a baud rate, defined as the number of bits transmitted per second. Each data frame begins with a start bit (logic 0), followed by a fixed number of data bits (typically 8, least-significant bit first), an optional parity bit, and a stop bit (logic 1).

Image source: ElectronicWings

Baud Rate Generation and Bit Timing

Because UART does not transmit a clock, each side generates timing internally. The bit period is defined as:

\[ \text{Bit Period} = \frac{1}{\text{Baud Rate}} \]

For example, at 9600 baud, each bit lasts approximately 104 microseconds. In RTL design, timing is expressed in clock cycles:

\[ \text{Clock Cycles per Bit} = \frac{\text{System Clock Frequency}}{\text{Baud Rate}} \]

With a 100 MHz clock and 115200 baud, this corresponds to 868 clock cycles per bit. Transmitters hold each bit for this duration, while receivers sample near the midpoint to maximize noise margin.

Common Pitfalls

Sampling too early or too late within a bit window can cause data corruption. Additionally, metastability can occur when sampling asynchronous inputs. Standard UART designs mitigate these issues using input synchronizers and mid-bit sampling strategies.

3. Designing the RX (Receive) FSM

The RX FSM reconstructs a parallel byte from serial data on the RX line. It monitors for a falling edge indicating a start bit, waits half a bit period, then samples each data bit at full bit intervals. Bits are captured LSB-first and assembled into a byte.

After receiving eight data bits, the FSM checks for a valid stop bit. If successful, the receiver asserts a one-cycle data-valid pulse and presents the received byte. A two-flip-flop synchronizer is used at the RX input to protect against metastability.

4. Designing the TX (Transmit) FSM

The TX FSM serializes parallel data onto the TX line. It remains idle with the line held high until a transmit request arrives. Transmission begins with a start bit, followed by data bits sent LSB-first, each held for one bit period.

After transmitting all data bits, a stop bit is asserted and the FSM returns to idle. Timing is controlled by a baud-rate counter derived from the system clock.

5. Top-Level Integration

The top-level module integrates RX and TX blocks around a shared timing parameter:

\[ \text{Clock Cycles per Bit} = \frac{\text{System Clock Frequency}}{\text{Baud Rate}} \]

The RX output byte is transformed using a simple bitwise inversion and immediately passed to the TX module. The RX data-valid pulse triggers TX transmission, creating a loopback-style behavior.

Loopback Self-Test

This design supports self-testing by echoing received bytes back to the sender. For example:

  • Send 0xA5 → Receive 0x5A
  • Send 0x55 → Receive 0xAA

6. Verification: Testbench & Simulation

The testbench generates a 100 MHz clock, applies reset, and drives UART frames onto the RX line. Each frame follows the standard UART format. A scoreboard verifies that transmitted data matches the expected inverted value.

The waveform shows correct sampling of start bits, data bits, and stop bits. The TX output reflects the inverted RX input, confirming correct end-to-end behavior.

7. On-Board Testing & Validation

A) USB-UART Adapter

An external USB-UART dongle can connect the FPGA to a PC terminal. Matching baud rate and frame settings (8-N-1) allows direct validation of UART functionality.

B) On-Chip CPU Self-Test

On Zynq platforms, the Processing System (PS) UART can be routed to Programmable Logic (PL) via EMIO. A bare-metal application can then act as an internal testbench.

This approach enables complete on-board validation without external hardware. Further details are covered in subsequent posts.
